# 伝え方

相手が誰かで 3 つに分かれる。常時効く分はそのエージェントの常時 load の file (`CLAUDE.md` の開始時の手順が並べる物) が持ち、ここは場面でだけ効く作法を持つ。

| 相手 | 渡す物 | 節 |
|---|---|---|
| 他チーム・他エージェント・別のタブ | 依頼文 | § 依頼文 |
| 操作者 (レビューや判断のために読む) | md | § 操作者に見せる文書 |
| 操作者 (自分で理解したい) | HTML のページ | § 説明のページ |

## 依頼文

別のタブへの送り方 (宛先・道具・届かなかった時) は、client の skill が持つ。ここは**相手に頼む文**の作法だけ。

操作者が中継する相手でも、タブどうしで直に送る相手でも、往復が増えると誰かの手間がその回数分増える。

- **1 通で完結させる**: 用件・困っている事実・判断に必要な材料を全部入れる。聞き返しが要る書き方が往復を生む
- **こちらの用件だけを書く**: 実装の形・工数・順序は相手の判断に残す。「〜すれば即対応できます」は相手の作業を決めつける形
- **形式を安定させる**: 用件 → なぜ必要か (こちら側の事実) → 判断を委ねる範囲。毎回同じ並びで書く
  - Why: 前提を docstring だけで立てて往復が出た件と、実装案を断定しすぎて相手の確認を生んだ件、どちらも中継の手間になった

## 操作者に見せる文書

操作者が見る・レビューする md (レビュー用の計画書・下書き・まとめ) の並べ方。

- **操作者に見てほしい物 (案・決めてほしい事・答え) を、file の一番上に置く**
  - Why: 書いた順に下へ足すと、見てほしい物が経緯の間に埋もれる。評価の目標の下書きで、書き直しの案が中ほどに埋もれ、並べ替えを求められた
- **経緯 (会議の解析・前の版・調べた事) は、その下に順序を付けて置く**。時系列か新しい順かを決め、見出しで分ける
- **後から案を足した時も、並べ直してから渡す**
- **推奨 (変更の案) は太字にし、1 件ずつ空行か箇条の印で区切る**
  - Why: 行頭が太字の行を空行なしで並べると、Markdown が全部を 1 つの段落につなぐ。レビューの所見 63 件の推奨が 1 つの塊になり、読めなかった
- 構造の決まりが既にある文書 (設計書・実装計画書・journal・テンプレートを持つ文書) は、その決まりに従う。この並べ方は、決まりが無い時の既定

## 説明のページ

### 背景 / 動機

計画書のような決めの文書とは別に、操作者が自分で理解するための「説明の文書」がある。操作者は図・表・数字で見える形の資料を随時ほしがり、その形は HTML のウェブページが一番見やすい。ページの置き場と辿り方を毎回同じにすると、エージェントは説明が要る時に何を作ればよいかが決まり、操作者は「どこに何があるか」をタブのメモから辿れる。

### 置き場

```
<階層>/pages/
├── index.html        階層のトップ (= タブの一覧。 読める名前はここに出す)
├── _template-tab/    タブのトップページの雛形 (= index.html。 client が写す)
├── _common/          ページが読む部品 (= 横の目次 toc-sidebar.js。 install_toc.py が根の真値から写す)
└── <タブの id>/      タブごと (= id は入れ替えでも変わらない)
    ├── index.html    そのタブのトップページ (= 今の全体像と、全部のページへのリンク)
    ├── memo.md       タブのメモ (= client の 📋 が開く。 git から外す)
    ├── <枝>/         中身で分けた folder (= 下の「中身の木」。 例: 前提/ 元の資料/ 実装/ 部品/ 結果/ 検証/ 会議/)
    │   └── <説明>.html
    ├── data/  src/   図の元のデータと、作り直す script
    └── <説明>.html   枝の folder を 1 つも持たないタブだけが、直下に置く
```

- **階層はタブを起動した階層**。親の階層で起動したタブは親の階層の `pages/` に置く。folder の運用の真値は `pages/_README.md`
- **説明は HTML のページにする**。図・表・数字で見せる。会話の外の公開の場には置かず、手元の file にしてエージェントの repo に commit して残す
- **説明のページと説明の資料は、タブの folder にだけ置く**。作業の folder・work repo・ダウンロードの folder には置かない。道具がほかの場所に書き出す物 (資料の pptx・PDF・資料の見え方の変換・作業の folder の要約) は、書き出したその手順の中で、タブのトップページに 1 行足す
  - Why: 案件の作業の folder に置いた図解と計画が、タブのトップから辿れなかった。操作者は 📋 から探して「消えた」と受け取った (2026-10-26 [操作者]「他のとこに説明用の資料置くな必ずリンクしろ」)
- **タブのトップページを、そのタブの説明の全部への唯一の入口にする**。メモに別の「トップページ」を書かない。メモに書いた path も全部トップページから辿れる形にする
- **説明のページを置いた後と渡す前に `scripts/check-tab-links.py <タブの folder>` を流し、抜けを 0 にする**。確かめるのは、枝の folder の中も含めて全部のページがトップから辿れるか・リンクの先が在るか・メモにだけ在る入口が無いか・横の目次を読む行が在るか・階層の部品が真値と同じか・枝を持つタブの直下にトップ以外のページが無いか

- **説明のページには、全部横の目次を付ける**。ページの `</body>` の前に部品を読む 1 行を置く。入れるのは `scripts/install_toc.py <ページか folder>` で、階層の `pages/_common/` へ部品を写し、ページから見た path で 1 行を足す (タブの folder のページなら `../_common/toc-sidebar.js`、枝の folder のページなら `../../_common/toc-sidebar.js`)。組み立ての script が書き出すページは、組み立ての元の雛形に、書き出し先から見た path で 1 行を入れる。部品の真値はエージェントの根の `pages/_common/toc-sidebar.js` で、直すのはそこだけにする
  - Why: 長いページで今どのあたりを見ているかが分からず、全部の節へ移る口も無かった (2026-11-04 [操作者]「サイドバーのような目次から全部へ移動できるページ構造にしてほしい。すべてのページがその構造であってほしい。今どのあたりを見ているかが分かりにくい」)
- **タブのトップページは client が作る**。タブの階層を記録した時に、無ければ雛形 `pages/_template-tab/index.html` を写し、埋め字 `{{title}}` と `{{tier}}` をタブの題と階層で埋める。在るページには触らない。説明のページを置いたら、そのページへの 1 行をタブのトップページに足す
- **階層のトップ `pages/index.html` には、タブが最初の説明のページを置いた時に、そのタブへの 1 行を足す**。説明の無いタブで一覧を埋めない
- 1 つの説明が長い時は、1 本の HTML の中をタブで章に分け、全部のタブの目次を付ける
- **1 つの頼み (例えば会議で出た宿題) の結果は、会議の枝のページに頼まれた事の表を置いて返す**。答えの中身は、中身の木のそれぞれの枝のページに書き、表からそこへリンクする。表の形は上の「会議のページ」のとおり
  - Why: 会議の宿題を段 1〜3 のページに分けて渡した時、どのページも中身は揃っていたのに、頼まれた事との対応がどこにも無く、操作者が自分で突き合わせることになった (2026-10-26 [操作者]「会議で何を求められて、何をやったのかが全然見えない。結局自分で見ないと分からない」)
- **段ごとに全部測った値 (例えば処理時間や量の内訳) を見せるページは、上から結論・流れの図・悪い所・全量の順に並べる**
  - 結論: その値で何が決まるか (例えば 1 回の処理時間から、答えを出せる間隔) を、今と直した時で並べる
  - 流れの図: 大きな単位の箱を入力から出力への処理の順に並べ、箱の色の濃さを全体の中の割合にし、直しのある箱と指摘のある箱に印を付ける。箱を押すと、下の全量の表のその行へ飛ぶ
  - 悪い所: 重い順に上位をいくつか並べ、1 件ずつ、なぜか・直しと効きの確かさ・人から受けた指摘と実物・コードの位置を付ける
  - 全量: いちばん下に置く。表は入力から出力への処理の順に並べ、各行にコードの位置と図へ戻るリンクを付ける。上のリンクは全部ここの行か節へ飛ぶ。並びの真値は data の file に置き、並べ替えた時は元の表と突き合わせて数が変わらないことを確かめる
  - Why: 内訳の表と試しの値を全部並べて渡した時、操作者はどこを見ればよいかが分からなかった。子の段を名前の順に並べた表は、処理の順に読めなかった (2026-10-27 [操作者]「入力から出口にかけてやって欲しい」)
- **図のデータは、作るための小さな script でページに埋め込み、元のデータはタブの folder の `data/` と `src/` に置く**。ページだけ開いても見え、作り直しは script を回すだけで済む

### 中身の木

- **ページの置き場は中身で決める**。タブの folder を枝の folder に分け、1 つの物の説明は、調べた日や会議の回によらず、その物の枝の 1 ページに集める。日付の順に並べるのは、検証と会議の一覧だけにする
  - 枝の例は、全体像 (トップページ)・前提 (依頼の中身とデータ)・元の資料 (論文や仕様)・今回の実装・部品ごとの仕組み (1 部品 1 ページ)・結果・検証 (1 本 1 ページ)・会議 (頼まれた事と答え)。枝の名前と数は仕事の種類で変えてよい
  - Why: 会議の回ごとに段のページを足していったタブで、1 つの部品の話が 4 ページに散り、元の論文の図に入口が無く、トップから何がどこに在るか分からなくなった (2026-11-05 [操作者]「定例で分けるんじゃなくて、全体像として調べたところ全部正しい場所に置いて欲しい」「モデルの説明ならモデルの説明の場所に置くべき。いつやったとか関係なく」「必要な時に必要なページを見に行くことが全然できない」)
- **新しく分かった事は、その中身の枝の今のページへ書き足す**。新しいページを作るのは、新しい部品か新しい検証のように、まだページの無い物の時だけにする
- **トップページは、いつも今の全体像だけを書き、上書きで直す**。並べるのは、何を確かめる仕事か・今の答え (分かった事・分かっていない事・次にやる事)・数の要約・全部の枝の順。枝の見出しの下に、その枝の全部のページへのリンクを置く。横の目次はトップページのリンクを並べるので、枝の中のページもトップから直にリンクする。枝の見出しとリンクを並べた節は、`data-toc-pages` を付けた要素 (`<section data-toc-pages>` など) で囲む。左の一覧はその中だけを読むので、全体像の文の中のリンクは一覧に出ず、ページは木の節に書いた名前で並ぶ
  - Why: 操作者は、開いた時に今どうなっているかを知りたい (2026-11-05 [操作者]「常に全体がどうなってるのかをちゃんと書くべき」)
- **ページの中の節の順は、ページの種類ごとに決まった順にする**
  - 部品のページ: 何をするか・入口と出口の形・重みか計算か・元の資料での作り・今回の作り・実物・この部品の検証へのリンク・コードの在処
  - 検証のページ: 問い (誰がいつ訊いたか)・答え・やった事・結果・まだ言えない事・関わる部品へのリンク・出所
  - 会議のページ: 頼まれた事を 1 つ 1 行で並べた表を置く。列は「頼まれた事」「やった事」「分かった事」「残り」の 4 つで、「頼まれた事」には言った人の言葉と記録のその時刻へのリンクを、「分かった事」には答えを持つ検証か部品のページへのリンクと出所を入れる
- **ページどうしを全部リンクでつなぐ**。検証のページから関わる部品のページへ、部品のページからその部品の検証へ、会議のページから答えを持つ検証へリンクする。新しい検証のページを足したら、関わる部品のページの「この部品の検証」にも 1 行足す

### 続けて保つ

- **階層の `pages/` の下には、生きているタブの folder だけを置く**。閉じたタブ・子のタブ・fork のタブの folder は、そのタブが閉じる時に片付ける。トップページが雛形のままで説明のページを持たない folder は消し、説明のページを持つ folder は、ページを持ち主のタブの木へ移してから、元を持ち主のタブの folder の `_archive/` に置く
- **子のタブや fork のタブが作った説明のページは、親のタブが自分の木の正しい枝へ移す**。移すのは子のタブを閉じる前で、元のページは親のタブの folder の `_archive/` に置く
- **木を変えた時と session を締める時に、木の全部を確かめ、見つけた抜けはその session で直す**。見るのは、リンクの抜け・枝の外に置いたページ・階層の `pages/` の下の生きていないタブの folder の 3 つ。リンクの抜けと枝の外のページは `scripts/check-tab-links.py` で、生きていないタブの folder は起動の検査の `pages_orphans` の行で見る
- **枝の folder を 1 つでも持つタブは、説明のページを全部枝の中に置く**。直下に置くのはトップページだけにする。枝の folder を持たない小さなタブは、直下にページを置いてよい。こう決めると、枝の外のページを検査が数えられる
  - Why: ページを中身の木に組み直した後も、階層の `pages/` の下に古いタブの folder が 9 つ残っていた。fork のタブが作った説明のページ 1 本と、閉じた子のタブの雛形のままのトップページ 8 つで、操作者が開いて何の物か分からなかった (2026-11-05 [操作者]「全部のページをちゃんとやれ。こういう管理もしろ。常に継続的にやれ」)

### 運用

- **メモは普通のメモとして書く**。タブのトップページへのリンクは client の画面が 📋 の頭に出すので、メモには書かない
  - Why: 操作者は 📋 から辿って全部の説明に届き、理解の往復が絵で早く進んだ。リンクを画面が固定で出すと、メモの書き直しで消えない
- **資料 (スライド・文書) を作る時は、ページを元にする**。説明の真値はページで、資料はそこから組み直す出力。社内・社外へ出す時は、ページを元に pptx などへ書き換える。資料の作法の skill を持つエージェントは、それに従う
- **渡す前に、画面なしのブラウザで、幅 390 px と 1280 px の 2 つで、はみ出しと JS の error を見る**。手順の skill `browser-use` を持つエージェントは、それに従う
- **ページを操作者に知らせる時は、操作者の端末で開ける tailnet の https の URL で渡す**。形は `https://<機械の tailnet の名前>:<ページの port>/<ページの origin の folder からの path>` で、ページの origin と port は client の設定 (`page_origin`) が決める。`localhost`・`127.0.0.1`・手元の file の path は渡さない。渡す前に、その URL が開けることを 1 回確かめる
  - Why: 操作者は別の端末から tailnet 越しに見ている。手元の口や path は、渡しても開けない
- **ページは全部残す**。社内・社外へ出す資料の元になる。古くなったページも、階層のトップからの辿り方で今の物と分けて置いておく

### 見本

操作者が作った物について言った言葉は、エージェントごとの file `samples.md` (この skill と同じ folder) に積む。型はこの file を配らない。**`samples.md` が在れば、ページを作る・直す前に、作る物の種類に当たる行を読んで従う**。この skill の決まりと食い違ったら、`samples.md` の操作者の言葉が勝つ

### 例外 / 適用範囲

- 計画書・設計書のような決めの文書は対象外。それぞれの決まりに従う
