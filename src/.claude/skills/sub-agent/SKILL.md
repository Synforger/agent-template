# 体の使い方

用語。 **統括** = 体を起動して成果を受け取る本人 (= 親の会話)。 **体** = sub-agent・Workflow の agent・子のタブの総称。

体を起動してよいか (= 操作者の許可が要るか) は、 そのエージェントの `rules/always.md` が決める。 体は統括の延長で、 `CLAUDE.md` と `profile/profile.md` の判断軸を踏襲させる。

**体の model は用途を問わず書く** (= 読むだけの体・レビューの体も同じ。 省くと統括の model を継ぎ、 小さい仕事に大きい model の費用が掛かる)。 既定は小さい model (= `sonnet`)。 Agent の道具は、 hook `subagent_model_gate.py` を入れた派生なら model を省いた起動が止まる。 Workflow の道具は script の `agent()` ごとに書く。 fork は統括の model でしか立たないので使わない。

## 体に何をさせるか (= 事故の根治はここ)

強く禁じても踏まれる。 **踏まずに済ませる道が一番楽な時だけ、 体はそちらを通る**。

- **体は commit までで停止、 PR を立てるのと merge は統括**。 体に許す git は `git add <path>` / `git commit` の 2 つだけ (= 退避・巻き戻し系は下の一覧)
  - Why: 緑かどうかの判定を体に握らせない (= 体の「緑になった」 を 1 つの round で 5 回差し戻し、 うち 4 回は難所を消して数字を良くする形だった。 出した事が区切りの口実にもなる)。 PR の前には統括にしか出来ない段 (= base が進んだ後の rebase / 必ず衝突する共有の表の解消 / 古くなった生成物の焼き直し) が挟まり、 体が先に立てるとその段の前の状態が PR として出る。 体が途中で止まっても編集は worktree に残る
  - **短い task は編集を worktree に置いたまま報告させ、 統括が `git diff` で受け取る** (= commit させないので踏めるコマンドが物理的に無くなる)
- **設計判断は統括が持つ**。 命名規則 / 所有権の判定 / 型の設計を体に発明させると必ず止まる (= 体は「推測で埋めるな」 を守っているだけ)。 規則は統括が決めて配る
- **削除を伴う task は `git show <commit>:<path>` の扱いを明示する**。 読むのは良いが**書き戻せば手書き復元と同じ**で緑でも成果ゼロ。 判定方法も渡す (= 生成器を消して回し直して同じものが出るか)
- **重い検証は「統括に測らせる」 と報告に書かせる** (= 体に待たせない、 下記 § 並列で出す時)

着手前に以下 3 行を必ず出力してから作業開始:
1. 私の役割 = <prompt から自己抽出>
2. 触る範囲 = <自スコープ path を列挙>

# 🚨 git (= 使うのは add / commit の 2 つだけ、 違反即 TaskStop)

- 使わないコマンド: `git checkout <file>` / `git stash` (= 全形態) / `git reset` (= 全形態) / `git revert` / `git restore`
  - 例外 = rebase / merge conflict 解消時の `--theirs` / `--ours` のみ (= 自スコープ file かつ完了報告で明示)
- **add は path 明示だけ** (= `git add -A` / `git add .` は `-- <path>` を付けても違反、 フラグ自体が対象)
- write は自スコープ path の中だけ (= 並列実行中の他の体の編集はそのまま置く)
- **上のコマンドは名前を出さずに言い換える** (= 「editor で書き戻し」 等の中立表現を使う)

判定はコマンド名だけで機械的に行う (= 「無害だから」「元に戻すだけ」 は判定に入れない)。

- **同期は `git fetch origin <base> && git rebase origin/<base>` だけ**。 `git reset --hard origin/<base>` は「内容差分ゼロ」 を確認しても**分岐点が古いまま残る**ので、 base が進んだ後の merge が**その間の PR を全部巻き戻す** (= 実測 8 本)

**衝動が出た時の合法代替**:
- 差分を見たい → `git diff <base> -- <file>` / `git diff --cached -- <file>` / `git show <base>:<file>` / `git status --short`
- stage を落としたい → 編集を手で undo + 必要 path だけ再 add (= 新規 file のみ `git rm --cached <path>`)
- lint の autoformat が scope 外 file に及んだ → **uncommitted 残置が正解**、 切り分けは不要、 NEW BUG REPORT 1 行で統括に渡す
- commit 後に消したい → 後続 commit で修正 (= 巻き戻さない)

# 完遂条件

- [ ] scope 内 write のみ (= `git diff --name-only <base>..HEAD` で他 path 0 件)

- [ ] 禁止語の検査 (= 番人) が文中 + ファイル名で 0 件 (= 止まったら理由を読んで中身を直す。 番人は外さない)

# 詰まったら報告する。 ただし進める形なら進む

**進みようが無い時** (= scope 不明 / 環境制約 / 設計判断要) は partial state を 1-3 行で報告して統括の判断待ち。

**回避を書ける時** (= 渡された規則に無理がある / 他の体の未着地を待っている) は**止まらない**。 回避を書いて進み、 報告に**撤去条件**を 1 行足す (= 「何が landed したら外すか」)。 統括が landed させたら、 撤去してから測り直す。

報告は 3 点で書く。 **揃っていない報告は統括が裏取りから始めることになり、 1 件あたりの往復が増える**:

```
症状 = <何が起きたか (= 出力の実物)>
真因 = <どこが原因か (= file:line)>
他 = <他の体にも出るか (= 自分以外の成果物を 1 つ見て判定)>
```

# 完了報告フォーマット

```
## やったこと
## やらなかったこと (= scope 内だが意図的に skip、 無ければ「なし」)
## 統括が必ず確認すべき 3 件 (= 1 件以上必須、 リスク / 判断保留 / scope 解釈の余地)
## 出力サマリ
Branch / commit / 変更ファイル / lint・test の状態 / 【⚠️ NEW BUG REPORT】(= 無ければ「なし」)
```

commit までで停止。 **PR と merge は統括**。

## 統括が埋める時のチェック

- [ ] 自スコープ path を **list 形式で明示** (= 曖昧な記述は scope 認識をずらす)
- [ ] 守る規則の欄に、 skill `code-writing` の今の版を書く (= frontmatter の `version`)
- [ ] branch 名 + commit prefix を具体的に指定 (= 体に判断させない)
- [ ] open-ended な scope (= 「最新化」「充実化」「reorg」) は**完了の定義を file 数 or 機能数で絞る** (= 絞らないと無限ループして watchdog kill)
- [ ] 「未着手」「未実装」 と認識したら `git show origin/<base>:<path>` で actual base を確認してから起動
- [ ] **待ちが絡む task は「何をどう確認して次へ進むか」 を手順で書く** (= 待つ対象 / 完了判定に見る文字列 / 判定できない時の再確認回数 / それでも不明なら partial 報告)。 体に通知は届かないので、 一文の「自分で確認して進めろ」 では永久停止する

## 渡した規則が変わったら版で伝える

全体にかかる規則は **file 1 枚に置いて版を持たせ、 体には path と版を渡す** (= 本文を prompt へ写さない)。 版を上げたら走っている体へ SendMessage で「v<N> を読め」 を送り、 体は報告に自分が実装した版を書く。
  - Why: 前提が外れたのに古い版で積まれた成果は、 緑でも意味が変わっている

## 並列で出す時

- **読むだけの task (= レビュー / 見直し) は別の決まりで割る** (= 見積もりと割り方 = `.claude/skills/review-rules/SKILL.md`。 下の「体数に上限なし」 は、 持ち場が重ならない書く作業の話)
- **割る線は成果物の最終形** (= 同時に書き換わる file の束)。**計画の刻み (= 段 / 箱 / Phase) で割らない**
  - How: 持ち場を切ったら**その持ち場の全部を 1 体に渡す** (= 刻みで割らない理由と計画書側の書式 = `.claude/skills/implementation-plan/SKILL.md`)
- **体に配るのは、 触る file が他の仕事と重ならない仕事だけ。 同じ file を触る仕事は、 統括が 1 本ずつ自分で書く** (= 機能ごとに分かれていても、 触る file が重なれば 1 本の仕事)
  - Why: 12 本のうち 8 本が同じ芯の file (= 型の値・頁の部品・本体の組み方・書き出し) を触っていたのに、 機能ごとに子へ配った実例がある。 載せ直しの衝突、 同じ名前の関数の衝突、 他の束の変更で古くなった表の書き換え、 写しの撮り直しが毎回出て、 同時に書く得は消え、 渡す本文・往復・合わせ込みだけが残った
  - How: 配る前に、 束ごとに触る file を並べ、 2 つの束に同じ file が出たら、 その束は配らずに自分で書く。 道を最後まで (= 組む所 → 書き出し → 検査) 読んでから並べる (= 書き出しの file を持ち場に入れ忘れて、 子が 2 本「足りない」 と返した)
- **走っている体に持ち場を足せる** (= 新しい wave を作らずに SendMessage 1 通)。 file が持ち場の線で割れているなら、 体を増やすより走っている体の scope を広げる
- **割る前に依存の向きを実物で確認する**。 ラッパー層は下位層と同じ wave に入れられない (= 書く先が無く write ゼロで止まる)。 「A は B を呼ぶだけの薄い層か」 を**実装 file を開いて**確かめる (= grep の件数は言及を数えるだけで実体を示さない)
- **sub-agent は「新しく書く所」 に使う** (= 1 行修正 / 既知箇所の置換 / 1 file の定型追随は自分で書いた方が速い)
- **並列なら worktree 隔離必須で、 切るのは統括** (= 体に同時に切らせると git の lock が競合し、 2 体が同じ checkout を共有して片方の変更が消えた)。 ハーネスの `isolation: "worktree"` が切るのは統括の repo だけなので、 別 repo を触る体には、 統括がその repo 側で `git worktree add` して path を渡す
- **体数に上限なし** (= path が disjoint な分は一斉に出す)
- **未達を数えたら残り全部に一度に体を当てる** (= 残り全部を一度に配り切る)
  - Why: 小分けは round を増やすだけで、 残りは毎回「次の round」 へ回る
  - How: ①残りを全部並べる ②各々に道を 1 行で付ける (= 判断が要るなら推奨で決め、 操作者に投げない) ③一度に配る
- **体が「壁」 と返したものは、 その場で引き取るか別の体へ渡す** (= 計画書へ転記して round を終わらせると「見た」 で止まる)
- **worktree は都度最新化 + 即削除**。 次の起動前に `git worktree list` で「進行中のみ」 を確認
- **完走した先行例を渡すと後続が到達し始める** (= 1 体が到達した形を数字つきで prompt に載せる)
- セッション上限で落ちた体は resume 不可だが**編集は worktree に残る**。 到達点を `git diff --numstat` で測って新しい体に渡す
- **引き取ったら体に SendMessage で伝える** (= 黙って merge すると、 起きた体が「worktree が消えた」 と誤診断して事実と違う報告を残す)
- **体は重い検証を統括へ渡して先に進む**。 待機中に session が終わって報告が出ない。 prompt に「重い build / test は**『統括に測らせる』 と報告に書いて先に進む**」 と書く
  - Why: 編集は worktree に残るが、 何をどこまでやったかが失われる
- **fork は統括だけが立てる**。 「investigation only」 と指示しても fork は自律的に commit する
- **名指しだけでは踏まれる**。 合法な代替を**表で隣に置く** (= 「退避しない、 commit する」「差分は `git diff` / `git show`」「scratch で壊すなら worktree の外」)
  - Why: 名指し禁止を読んだうえで 4 体が踏み、 全員が自己申告した。 代替を置いた後は報告が出ていない

## 並列 fleet を中央で受け取る時の 3 手

- **共有表 (= adapter の登録先など) は必ず衝突する。** 解消は**「両方を残す」 の一手**に決め打つ
- **rebase は source の mtime を進めるので成果物の鮮度 gate が落ちる。** merge 前にその binding の build を 1 回踏む
- **`task lint | tail` の後の `$?` は tail の値。** exit code は単独で取る

## 子のタブ (= session をまたいで回る体)

Agent tool の体は親の会話の中でしか動けず、 自動の入れ替えで親の会話が替わると一緒に消える。 子のタブは client (= 画面の配信と入れ替えを持つ道具) の一覧に出るエージェントのタブで、 自分の会話と自分の入れ替えを持つので、 親が替わっても回り続ける。 **立てる・閉じるは統括の判断で行う** (= 起動の許可が要る Agent tool / Workflow tool とは別)。 命令 (= `tabs new` / `tabs children` / `tabs send` / `tabs close` / 子の側の `tabs report`) の使い方と、 子の側の手順は client の plugin の skill `pwa-client:tabs` が持つ (= 子の側のエージェントの決まりは § 子の側の決まり)。

- 体の決まりはこの skill の上の節と同じ (= 渡す本文は § prompt テンプレ、 git は commit まで、 worktree は統括が切る、 PR と merge は統括、 中央で受け取る時の 7 点)
- **子は親と同じ階層に立つ** (= 立てる命令が親の階層を渡す。 本文の検査は「子は親と同じ境界を読む」 前提で通るので、 違う階層の子には親だけが読んだ物が通ってしまう)
- **子の model は client の起動設定が決める** (= 既定は小さい model で、 親は大きい model のまま)
- **同時に持てる子の数には client の上限がある** (= 設定 `child_sessions_max`)。 子は同じ口座の使用量を分け合う
- **子は自分の worktree と branch で作業する** (= 「同時作業 branch 1 本」 の例外は子の分だけ)。 エージェント自身の file を直す子にも worktree を切って渡す (= 親と同じ checkout の主 branch に 2 本が同時に書かない)

### 立てる

1. worktree を切る (= work repo は `git worktree add <path> -b feature/<scope> origin/<base>`、 エージェント自身の repo は同じ形で `child/<scope>`)。 **その repo の試験の環境が worktree の中で立つことを確かめてから渡す** (= 準備の命令を持つ repo はそれを流してから。 `uv run` と `pnpm` で組む repo は準備が要らないので、 軽い試験を 1 本流して通ることを見る)
   - Why: 環境の無い worktree を渡すと子がそれぞれ別の python で環境を作り、 統括が重ねた準備で `python` と `pip` が別の版を指して、 全体の試験を 2 回流し直した。 主の checkout の環境で流すと、 試験が主の checkout の code を読むので代わりにならない
2. 本文を file に書く (= § prompt テンプレを埋め、 worktree の path と branch、 完了の定義、 返し方 = `tabs report done|stuck` を入れる)
3. `tabs new "<題>" <本文の file>` (= 子の id とメモの path が出る。 題は一覧に出る名前なので、 何の仕事かが読める語で)

### 見る

- `tabs children` (= 子ごとの id / 状態 / 題)。 状態は子のメモが持つ (= 作業中 / 完了 / 詰まり)
- 入れ替わった親は、 起動の検査の `children:` の行で自分の子を知る (= タブの id は入れ替えで変わらないので、 子は前の会話が立てた物でも自分の子として出る)
- 子の報告は親のタブへの連絡として届く (= 本文が「子のタブ <id> の報告 (完了 / 詰まり)」)

### 回収する

**終わった子は必ず引き取り、 片付けまで 1 回で行う**。

1. 報告を一次ソースで確かめる (= § 中央 merge の責務 の 7 点。 子の「緑」 は自分で取り直す)
2. 差し戻すなら、 子へ `tabs send <子の id> <file>` で返す (= 閉じない)
3. 取り込んだら PR → merge、 worktree と branch を消す
4. `tabs close <子の id>` (= タブとそのメモが消える。 作業中の子は `--force` の時だけ)
5. journal の「やったこと」 に子の id と成果を書く (= 子は journal を書かない)

詰まった子は、 判断を返して続けさせるか、 引き取って閉じる。 起動の検査が `完了` か `詰まり` を 1 本でも出したら、 その session のうちに回収する。
### 子の側の決まり (= 子のタブとして動く時。 手順の本体は skill `pwa-client:tabs § Working as a child`)

見分けは環境変数 `AGENT_CHILD=1`。 手順に次のエージェントの決まりを足す。

- **起動と締めは、 `CLAUDE.md` の開始時と終了時の手順の代わりに、 この節と skill `pwa-client:tabs` で行う** (= 子に親と同じ起動の読み込みをさせない)。 読むのは `rules/always.md` と `profile/profile.md` と親が渡した仕事 (= 最初の発話の本文。 自動の入れ替えで起動し直した時は、 タブのメモ `$PWA_NOTE` の「渡された仕事」 と「引き継ぎ」)。 journal / vision / 起動の検査 / ブリーフィングは無く、 エージェントの pull も起動の script が飛ばす (= 親が同じ clone で作業している)
- 読了は 1 行で出し、 挨拶もブリーフィングもせずに仕事へ入る。 着手の前に、 § prompt テンプレと同じ 3 行の復唱を出す
- 子は journal の代わりにタブのメモの `## 引き継ぎ` に続きを書く (= 締めの skill `session-end` は親の物)
- エージェント自身の file を直す仕事でも、 親と同じ checkout の主 branch には commit しない (= 渡された worktree と branch の中で commit まで)
- 操作者がこのタブで直に打った発話は、 普通の操作者の発話として扱う (= GO の判定は `rules/always.md`)


## 中央 merge の責務

体は commit までで停止、 PR を立てるのと merge は統括。 **PR は下の 7 点を統括が取り直した後に立てる** (= 本文に書くのは統括が実測した事。 赤か未達が残る間は branch に置く)。 branch flow の真値 = `rules/always.md § git`。

**他人のコードを引き継ぐ開発者の気分で diff 全文を疑う**:

1. scope 外を触っていないか (= `git diff --name-only base..HEAD`)
2. 手元 CI 全緑か (= 体の報告だけで信用せず、 走らせられるなら走らせる)
3. 禁止語の検査が文中とファイル名の両方で 0 件か
4. 既存パターンを真似ているか、 別構造を持ち込んでいないか
5. コメント / 変数名 / docstring が drift していないか
6. テストが本当に意味を持つか (= `assert 0 == 0` 系、 mock だらけで実体を verify していないもの)
7. 「動いてた仕様」 を変えていないか

- **緑の判定は統括が自分で取り直す**。 違和感があれば差し戻す (= 「体が緑にしたから OK」「まあいいか」 では merge しない)
- **取り直すのは全体の試験と写しの比べ (= 数分で終わる物) まで。 重い検査 (= 壊し方の表のように 1 本で数分〜数十分かかる物) は、 その日の束を全部 merge した後に 1 回だけ流す** (= 赤が出たら、 その表の束へ戻って直す)
  - Why: 子が流した壊し方の表を、 統括が束ごとにもう一度流した実例がある (= 1 本 27 分の表もあった)。 統括の確かめは 1 本ずつなので、 終わった子が順番待ちで並び、 待ちが時間の大部分になった
- 承認なら squash + delete-branch、 merge 後に worktree 削除 + local branch 削除まで 1 サイクルで完遂
- merge 順序は依存に沿う (= lint を入れる PR が先、 違反 fix が後)。 同じ infra file を複数の体が触ると conflict するので 1 PR ずつ片付ける
- 体が返した **NEW BUG REPORT は同 session 内で振り分ける**。 設計判断ゼロ + 1-3 file + 既存 test で担保 + 挙動変化ゼロ の 4 条件が全部揃うなら黙って潰して結果報告、 1 つでも欠けるなら「bug 概要 + 範囲 + 設計判断点」 を 3-5 行で操作者に出す
