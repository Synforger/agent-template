# 体の使い方

用語。**統括** = 体を立てて成果を受け取る本人 (親の会話)。**体** = 子のタブ。

体は統括の延長で、`CLAUDE.md` と常時 load の file (`CLAUDE.md` の開始時の手順が並べる物) の判断軸を踏襲させる。

**サブエージェント (Agent の道具・fork) と Workflow の道具は使わない**。hook `subagent_gate.py` が全部止める。サブエージェントは操作者の一覧に出ず、話しかけられず、親の会話が入れ替わると一緒に消える。読む仕事は統括が自分で読み、書く仕事は子のタブに渡し、別の model の意見が要る時は § 別の model の読み手と、書き直しの書き手 に渡す。

## 体に何をさせるか (事故の根治はここ)

強く禁じても踏まれる。**踏まずに済ませる道が一番楽な時だけ、体はそちらを通る**。

- **体は commit までで停止、PR を立てるのと merge は統括**。体に許す git は `git add <path>` / `git commit` の 2 つだけ。退避・巻き戻し系の扱いは下の一覧
  - Why: 緑かどうかの判定を体に握らせないためだ。体の「緑になった」を 1 つの round で 5 回差し戻し、うち 4 回は難所を消して数字を良くする形だった。出した事が区切りの口実にもなる。PR の前には統括にしか出来ない段が挟まり、base が進んだ後の rebase / 必ず衝突する共有の表の解消 / 古くなった生成物の焼き直しが当たる。体が先に立てるとその段の前の状態が PR として出る。体が途中で止まっても編集は worktree に残る
  - **短い task は編集を worktree に置いたまま報告させ、統括が `git diff` で受け取る**。commit させないので踏めるコマンドが物理的に無くなる
- **設計判断は統括が持つ**。命名規則 / 所有権の判定 / 型の設計を体に発明させると必ず止まる。体は「推測で埋めるな」を守っているだけだ。規則は統括が決めて配る
- **削除を伴う task は `git show <commit>:<path>` の扱いを明示する**。読むのは良いが**書き戻せば手書き復元と同じ**で緑でも成果ゼロ。判定方法も渡す。例えば生成器を消して回し直して同じものが出るかを見る
- **重い検証は「統括に測らせる」と報告に書かせる**。体に待たせない。詳しくは下記 § 並列で出す時

## prompt テンプレ

親が書くのは、子ごとに違う欄だけにする。子が毎回守る決まった行 (復唱・git・詰まった時・操作者の画面と手・完了報告の形・共通の完了の条件) は § 子の側の決まり に在り、子が着手の前に 1 回読む。親が毎回書き写さない。
  - Why: 決まった約 80 行を、親が子を立てるたびに全部書いていた。同じ物を何度も書かせる形をやめる

````
skill `sub-agent` の § 子の側の決まり を読んでから着手する。

# 全体像

- base = <base branch の名前>
- <plan の path、base の tip、並列の状況、前の段の PR など>

# あなたのスコープ

<何をやるかを file path の単位で明示する。設計判断を含むなら、操作者が確定した選択を明記する>

# 自分の scope の path (write はこの中だけ)

- <scope file path>
- <READ only path> (確かめるために読むだけ)

# 守る規則の版

- コードの書き方 = `.claude/skills/code-writing/SKILL.md` の版 <N>

# 完了の条件 (共通の物に足す分だけ)

- [ ] <この仕事に固有の条件。無ければ行ごと消す>
````

## 統括が埋める時のチェック

- [ ] 自スコープ path を **list 形式で明示**。曖昧な記述は scope 認識をずらす
- [ ] 守る規則の欄に、skill `code-writing` の今の版を書く (frontmatter の `version`)
- [ ] branch 名 + commit prefix を具体的に指定。体に判断させない
- [ ] open-ended な scope (「最新化」「充実化」「reorg」) は**完了の定義を file 数 or 機能数で絞る**。絞らないと無限ループして watchdog kill になるからだ
- [ ] 「未着手」「未実装」と認識したら `git show origin/<base>:<path>` で actual base を確認してから起動
- [ ] **待ちが絡む task は「何をどう確認して次へ進むか」を手順で書く**。手順に入れるのは、待つ対象 / 完了判定に見る文字列 / 判定できない時の再確認回数 / それでも不明なら partial 報告。体に通知は届かないので、一文の「自分で確認して進めろ」では永久停止する

## 渡した規則が変わったら版で伝える

全体にかかる規則は **file 1 枚に置いて版を持たせ、体には path と版を渡す**。本文を prompt へ写さない。版を上げたら走っている子へ `tabs send` で「v<N> を読め」を送り、体は報告に自分が実装した版を書く。
  - Why: 前提が外れたのに古い版で積まれた成果は、緑でも意味が変わっている

## 別の model の読み手と、書き直しの書き手

**読み手と書き手は子のタブに渡す。`claude -p` を使うのは、操作者が API の利用 (API の key で動かす) を明示した仕事だけにする**。口座のログインで動かす仕事を安くする工夫は、ターミナルで動く子のタブの側で行う。
  - Why: 公式の headless のページは、口座のログインを読まない `--bare` を将来 `-p` の既定にすると書いている。client もターミナルのまま使うと決めた (2026-11-18 [操作者]「んじゃ変えない方がいいな。」、2026-11-21 [操作者]「ターミナルでも同じくらい安くないといけない。」「それを使っていいのは俺が明示的にapi利用がある時だよ。」)

- **文書を書き直すだけの仕事は、子のタブ 1 体に渡す**。決まりの file には、変えてはいけない物・書き方・言葉の対応表を書き、書き直した全文を受け取る。前後が同じ物を指すかは `.tooling/docs-check/check-rewrite-keeps.py` と同じ形の機械の比較で確かめ、統括は全文を読む
- **別の model の意見 (設計書の 1 周目の読み手・決める前の議論) も、子のタブに渡す**。子の model は起動の script `.tooling/lib/claude-launch.py` の `CHILD_MODEL` が決める。問いと、読ませる file の path を渡し、返事の指摘は統括が実物で確かめてから採る。使い方の場面は skill `review-rules`

## API とサブスクの使い分け

**API の key で動かすのは本番だけにし、試験はサブスク (そのタブの口座のログイン) で動かす**。試験は、言語 model を呼ぶ試し・検証・採点・計測の全部。どのタブ・どの道具でも同じ。
  - Why: 操作者が財布の線を本番と試験で引いた (2026-11-22 [操作者]「どのタブでも全てapi使うのは本番試験はサブスクが配備されて欲しい。」)
  - How: program から呼ぶ試験は聞かれるタブ (`tabs ask`)、読み手と書き手は子のタブ。偽物の client で回る自動の試験はそのまま。道具の試しの口は、本番の key を既定で読まない形にする
- **資料は、その境界が使う口座の中で試す**。試験をサブスクへ移すために、境界の中の資料を別の口座のタブへ渡さない
- **API でしか確かめられない試験 (API そのものの形・請求の確かめ) は、流す前に操作者に訊く**

## 並列で出す時

- **読むだけの task (レビュー / 見直し) は別の決まりで割る**。見積もりと割り方は `.claude/skills/review-rules/SKILL.md` が持つ。下の「体数に上限なし」は、持ち場が重ならない書く作業の話
- **割る線は成果物の最終形** (同時に書き換わる file の束)。**計画の刻み (段 / 箱 / Phase) で割らない**
  - How: 持ち場を切ったら**その持ち場の全部を 1 体に渡す**。刻みで割らない理由と計画書側の書式は `.claude/skills/implementation-plan/SKILL.md` が持つ
- **体に配るのは、触る file が他の仕事と重ならない仕事だけ。同じ file を触る仕事は、統括が 1 本ずつ自分で書く**。機能ごとに分かれていても、触る file が重なれば 1 本の仕事
  - Why: 12 本のうち 8 本が同じ芯の file (型の値・頁の部品・本体の組み方・書き出し) を触っていたのに、機能ごとに子へ配った実例がある。載せ直しの衝突、同じ名前の関数の衝突、他の束の変更で古くなった表の書き換え、写しの撮り直しが毎回出て、同時に書く得は消え、渡す本文・往復・合わせ込みだけが残った
  - How: 配る前に、束ごとに触る file を並べ、2 つの束に同じ file が出たら、その束は配らずに自分で書く。道を最後まで (組む所 → 書き出し → 検査) 読んでから並べる。書き出しの file を持ち場に入れ忘れて、子が 2 本「足りない」と返した例がある
- **走っている体に持ち場を足せる**。新しい wave を作らずに `tabs send` 1 通で足せる。file が持ち場の線で割れているなら、体を増やすより走っている体の scope を広げる
- **割る前に依存の向きを実物で確認する**。ラッパー層は下位層と同じ wave に入れられない。書く先が無く write ゼロで止まるからだ。「A は B を呼ぶだけの薄い層か」を**実装 file を開いて**確かめる。grep の件数は言及を数えるだけで実体を示さない
- **子のタブは「新しく書く所」に使う**。1 行修正 / 既知箇所の置換 / 1 file の定型追随は自分で書いた方が速い
- **並列なら worktree 隔離必須で、切るのは統括**。体に同時に切らせると git の lock が競合し、2 体が同じ checkout を共有して片方の変更が消えたためだ。統括が書く file を持つ repo で `git worktree add` して path を渡す (§ 立てる)
- **体数に上限なし**。path が disjoint な分は一斉に出す
- **未達を数えたら残り全部に一度に体を当てる**。残り全部を一度に配り切る形にする
  - Why: 小分けは round を増やすだけで、残りは毎回「次の round」へ回る
  - How: ①残りを全部並べる ②各々に道を 1 行で付ける。判断が要るなら推奨で決め、操作者に投げない ③一度に配る
- **体が「壁」と返したものは、その場で引き取るか別の体へ渡す**。計画書へ転記して round を終わらせると「見た」で止まる
- **worktree は都度最新化 + 即削除**。次の起動前に `git worktree list` で「進行中のみ」を確認
- **完走した先行例を渡すと後続が到達し始める**。1 体が到達した形を数字つきで prompt に載せる
- 使用量の上限で止まった子は、上限が戻ると client が続けさせる。**編集は worktree に残る**ので、引き取る時は到達点を `git diff --numstat` で測る
- **引き取ったら子に `tabs send` で伝える**。黙って merge すると、起きた体が「worktree が消えた」と誤診断して事実と違う報告を残す
- **体は重い検証を統括へ渡して先に進む**。待機中に session が終わって報告が出ない。prompt に「重い build / test は**『統括に測らせる』 と報告に書いて先に進む**」と書く
  - Why: 編集は worktree に残るが、何をどこまでやったかが失われる
- **名指しだけでは踏まれる**。合法な代替を**表で隣に置く**。例えば「退避しない、 commit する」「差分は `git diff` / `git show`」「scratch で壊すなら worktree の外」が当たる
  - Why: 名指し禁止を読んだうえで 4 体が踏み、全員が自己申告した。代替を置いた後は報告が出ていない

## 並列 fleet を中央で受け取る時の 2 手

- **共有表 (adapter の登録先など) は必ず衝突する。** 解消は**「両方を残す」の一手**に決め打つ
- **rebase は source の mtime を進めるので成果物の鮮度 gate が落ちる。** merge 前にその binding の build を 1 回踏む

## 子のタブ (session をまたいで回る体)

子のタブは client (画面の配信と入れ替えを持つ道具) の一覧に出るエージェントのタブで、自分の会話と自分の入れ替えを持つので、親が替わっても回り続ける。**立てる・閉じるは統括の判断で行う**。命令 (`tabs new` / `tabs children` / `tabs send` / `tabs close` / 子の側の `tabs report`) の使い方と、子の側の手順は client の plugin の skill `pwa-client:tabs` が持つ。子の側のエージェントの決まりは § 子の側の決まり。

- 体の決まりはこの skill の上の節と同じ。渡す本文は § prompt テンプレ、git は commit まで、worktree は統括が切る、PR と merge は統括、中央で受け取る時の 7 点が当たる
- **子は親と同じ階層に立つ**。立てる命令が親の階層を渡す。本文の検査は「子は親と同じ境界を読む」前提で通るので、違う階層の子には親だけが読んだ物が通ってしまう
- **子の model は client の起動設定が決める**。既定は小さい model で、親は大きい model のまま
- **子に渡すのは、決め方 (値・形・合格の条件) が操作者と決まっている仕事だけにする**。決まっていない仕事は、親が操作者と決めてから渡す。決まる前に配ると、決まった後に配り直す分が 2 度手間になる (2026-11-12 [操作者]「なんかあんまりなんも決まってないのにバンバンこたぶ動かさないで欲しいわ。普通に無駄になりそう。」)
- **子の数は仕事の分け方だけで決める**。持ち場の重ならない仕事ごとに 1 体を立て、いちばん早く閉じる形に広げる。報告なしで止まった子は、client の見張りが親へ `<child-stopped>` で知らせる。子は同じ口座の使用量を分け合う
- **子は自分の worktree と branch で作業する**。「同時作業 branch 1 本」の例外は子の分だけ。エージェント自身の file を直す子にも worktree を切って渡す。親と同じ checkout の主 branch に 2 本が同時に書かないようにするためだ

### 立てる

0. `tabs capacity` で、この機械の空きメモリと口座の使用量を見る。子は親と同じ口座の使用量を分け合う。数の上限は無く、線も引かれていないので、読んで決めるのは統括
1. `git fetch origin <base>` の後に worktree を切る (base の今の先端から切る。古い木から切った子が持ち場の外の file の今を読み違えた、2026-11-15)。work repo は `git worktree add <path> -b feature/<scope> origin/<base>` で、エージェント自身の repo は同じ形で `child/<scope>` を切る。**子が書く file を持つ repo で切る**: 階層の folder が自前の `.git` を持つ別の repo なら (`git -C <書く file の folder> rev-parse --show-toplevel` で確かめる)、エージェントの根ではなくその repo で切る。根で切ると、書く先が worktree に入らない (2026-11-08、会社の階層の file を書く子に根の worktree を渡し、子が会社の階層の主 branch に直に commit した)。**その repo の試験の環境が worktree の中で立つことを確かめてから渡す**。準備の命令を持つ repo はそれを流してから渡す。`uv run` と `pnpm` で組む repo は準備が要らないので、軽い試験を 1 本流して通ることを見る
   - Why: 環境の無い worktree を渡すと子がそれぞれ別の python で環境を作り、統括が重ねた準備で `python` と `pip` が別の版を指して、全体の試験を 2 回流し直した。主の checkout の環境で流すと、試験が主の checkout の code を読むので代わりにならない
2. 本文を file に書く。§ prompt テンプレを埋め、worktree の path と branch、完了の定義、返し方 `tabs report done|stuck` を入れる。**親の指示や別の子の着地を待たせる子には、待つ前に `tabs report stuck` で何を待つかを報告するよう書く**
3. `tabs new "<題>" <本文の file> [--model <名前>] [--effort <段>]`。子の id とメモの path が出る。題は一覧に出る名前なので、何の仕事かが読める語で付ける
   - **model と effort は仕事の種類で選ぶ**。実装は付けずに既定で立てる。決まった形への書き直しと定型の追随は `--effort medium`、別の model の意見は親と別の model を `--model` で選び effort は既定のままにする。既定・許す値・子から外す道具は、エージェントの `templates/claude-child.json` が持つ。許されない値は既定で立ち、子の最初の発話の `[起動の知らせ]` の行に出る
     - Why: 子は呼ぶたびに起動の固定分と会話を読み直す。中身の決まった仕事で考える量を下げると、確かめと探索が減り、使用量が下がる (2026-11-21、子から使わない道具を外して 1 回目の文脈を 4.66 万から 2.48 万にした時に、同じレビューで読み直しが 150 万から 51 万になった)

### 見る

- `tabs children` (子ごとの id / 状態 / 題)。状態は子のメモが持つ (作業中 / 完了 / 詰まり)
- 入れ替わった親は、起動の検査の `children:` の行で自分の子を知る。タブの id は入れ替えで変わらないので、子は前の会話が立てた物でも自分の子として出る
- 子の報告は親のタブへの連絡として届く。本文は「子のタブ <id> の報告 (完了 / 詰まり)」の形

### 回収する

**終わった子は必ず引き取り、片付けまで 1 回で行う**。

1. 報告を一次ソースで確かめる。確かめは § 中央 merge の責務 の 7 点で、子の「緑」は自分で取り直す
2. 差し戻すなら、子へ `tabs send <子の id> <file>` で返す。閉じない
3. 取り込んだら PR → merge、worktree と branch を消す
4. `tabs close <子の id>`。タブとそのメモが消える。作業中の子は `--force` の時だけ閉じる
5. journal の「やったこと」に子の id と成果を書く。子は journal を書かない

- **次の仕事をキャッシュの持ち時間 (prompt cache の TTL) の中で渡す子だけ、閉じずに残すか `tabs sleep` で眠らせる。それより空くなら閉じ、次の仕事は新しい子に渡す**
  - Why: キャッシュは最後に使ってから持ち時間で消える。大きくなった会話を後から起こすと、会話の全体をキャッシュへ書き直すので、起動の固定分から始まる新しいタブより高くつく。持ち時間の中なら、安い読み直しで続けられ、覚えた中身も使える (2026-11-21 [操作者]「子タブはそもそもコンテキスト食ってる場合再会が1時間以上なら使わない方がいいな」)

詰まった子は、判断を返して続けさせるか、引き取って閉じる。起動の検査が `完了` か `詰まり` を 1 本でも出したら、その session のうちに回収する。

- **報告した子へ仕事を足して返す時は、本文の最後に「済んだら `tabs report done|stuck` で報告してから止まる。まだ待つ物が在れば stuck に書く」と書く**。印の無い `tabs send` は子のメモを `作業中` に戻すので、「今の stuck のままで良い」と返すと、子は報告せずに止まり、client の見張りが親に知らせる。仕事を足さない返事 (了解・知らせ) は `tabs send <子の id> <file> --no-work` で送り、メモを報告のままにする (2026-11-15、1 つの親で子 3 本に起きた)

### 子の側の決まり (子のタブとして動く時。手順の本体は skill `pwa-client:tabs § Working as a child`)

見分けは環境変数 `AGENT_CHILD=1`。手順に次のエージェントの決まりを足す。

- **起動と締めは、`CLAUDE.md` の開始時と終了時の手順の代わりに、この節と skill `pwa-client:tabs` で行う**。子に親と同じ起動の読み込みをさせない。読むのは `CLAUDE.md` の開始時の手順が並べる常時 load の file と、親が渡した仕事。親が渡した仕事は最初の発話の本文にあり、自動の入れ替えで起動し直した時は、タブのメモ `$PWA_NOTE` の「渡された仕事」と「引き継ぎ」にある。票を渡されていれば `tabs ticket mine` も読む。journal / vision / 起動の検査 / ブリーフィングは無く、エージェントの pull も起動の script が飛ばす。親が同じ clone で作業しているためだ
- 読了は 1 行で出し、挨拶もブリーフィングもせずに仕事へ入る
- **着手の前に 3 行を出す**: 1. 私の役割 2. 触る範囲 (自分の scope の path) 3. 読むだけの範囲。認識が親の本文とずれていたら、推測で進めずに親に確かめる
- **git は `git add <path>` と `git commit` の 2 つだけ**。巻き戻しと退避の命令 (checkout で file を戻す・stash・reset・revert・restore) は使わない。例外は rebase と merge の衝突を解く時の `--theirs`・`--ours` で、自分の scope の file に限り報告に書く。add は path を名指し、`-A` と `.` は付けない。write は自分の scope の中だけで、並列の子の編集はそのまま置く。同期は `git fetch origin <base> && git rebase origin/<base>` だけ (reset で合わせると分岐点が古いまま残り、base が進んだ後の merge がその間の PR を巻き戻す。実測 8 本)
  - 代わりの手: 差分は `git diff`・`git show <base>:<file>`・`git status --short`。stage を落とすなら編集を手で戻して要る path だけ add し直す (新規 file は `git rm --cached <path>`)。lint の自動整形が scope の外に及んだら commit せずに置き、報告の NEW BUG REPORT に 1 行。commit の後に消したい物は後の commit で直す
- **共通の完了の条件**: write は scope の中だけ (`git diff --name-only <base>..HEAD` で他の path が 0 件)・当たる試験と lint と docs-check が clean (外した・飛ばした試験が 1 本でもあれば完了とは言わず、その名前と理由を stuck で返す)・番人の禁止語の検査が 0 件 (止まったら理由を読んで中身を直し、番人は外さない)・commit の prefix が規約どおり・生成の道具の署名行を footer に入れない・diff を通読し、最低 1 本は file 全体を開く。PR と merge は親が持つ
- **詰まったら**: 進みようが無い時 (scope が不明・環境の制約・設計判断が要る) は途中の状態を `tabs report stuck` で返して待つ。回避を書ける時 (規則に無理がある・別の子の着地を待つ) は止まらずに回避を書き、報告に撤去の条件を 1 行足す。報告は「症状 = 出力の実物 / 真因 = file:line / 他 = 他の子にも出るか」の 3 点で書く
- **操作者の画面に出る物** (許可の画面・試験の窓・通知) は親の返事の後に出す。操作者に押す・答える・打つを頼む前に、画面に何が出るかを確かめて報告に書く
- **完了報告の形**: `## やったこと` / `## やらなかったこと` (無ければ「なし」) / `## 親が必ず確かめる物` (1 件以上) / `## 出力のまとめ` (branch・commit・変更した file・lint と試験の状態・NEW BUG REPORT、無ければ「なし」)。commit までで止まる
- 子は journal の代わりにタブのメモの `## 引き継ぎ` に続きを書く。締めの skill `session-end` は親の物
- **`tabs report` に渡す報告の file と、build や試験の log は、階層の `_scratch/<自分のタブの id>/` に書く**。`pages/<自分のタブの id>/` に置けるのは、操作者に見せる説明のページとタブのメモだけ (`pages/_README.md`)。そこに置いた md は docs-check が frontmatter の無い file として赤にする (2026-11-09、子 2 本が報告の md と log をページの folder に置いた)
- **親の指示や別の子の着地を待つ時は、待つ前に `tabs report stuck <file>` で何を待つかを書く**。メモが作業中のまま入力待ちで止まると、client の見張りが報告なしで止まった子として親に知らせる (2026-11-09、待つ子 1 本で親に 5 回届いた)
- エージェント自身の file を直す仕事でも、親と同じ checkout の主 branch には commit しない。渡された worktree と branch の中で commit までを行う
- 操作者がこのタブで直に打った発話は、普通の操作者の発話として扱う。頼みの扱いは `rules/always.md` が持つ


## 中央 merge の責務

体は commit までで停止、PR を立てるのと merge は統括。**PR は下の 7 点を統括が取り直した後に立てる**。本文に書くのは統括が実測した事。赤か未達が残る間は branch に置く。branch flow の真値 = `rules/always.md § git`。

**他人のコードを引き継ぐ開発者の気分で diff 全文を疑う**:

1. scope 外を触っていないか (`git diff --name-only base..HEAD`)
2. 全体の試験が緑か。公開の repo は PR の Actions の結果で見て、手元では流さない。private の repo は手元で 1 回流す。体の報告だけで信用しない
3. 禁止語の検査が文中とファイル名の両方で 0 件か
4. 既存パターンを真似ているか、別構造を持ち込んでいないか
5. コメント / 変数名 / docstring が drift していないか
6. テストが本当に意味を持つか。`assert 0 == 0` 系と、mock だらけで実体を verify していないものが当たる
7. 「動いてた仕様」を変えていないか

- **緑の判定は統括が自分で取り直す**。違和感があれば差し戻す。「体が緑にしたから OK」「まあいいか」では merge しない
- **取り直すのは、上の 2 の全体の試験と写しの比べまで。重い検査 (壊し方の表のように 1 本で数分〜数十分かかる物) は、その日の束を全部 merge した後に 1 回だけ流す**。赤が出たら、その表の束へ戻って直す
  - Why: 子が流した壊し方の表を、統括が束ごとにもう一度流した実例がある (1 本 27 分の表もあった)。統括の確かめは 1 本ずつなので、終わった子が順番待ちで並び、待ちが時間の大部分になった
- 承認なら squash + delete-branch、merge 後に worktree 削除 + local branch 削除まで 1 サイクルで完遂
- merge 順序は依存に沿う (lint を入れる PR が先、違反 fix が後)。同じ infra file を複数の体が触ると conflict するので 1 PR ずつ片付ける
- 体が返した **NEW BUG REPORT は同 session 内で振り分ける**。設計判断ゼロ + 1-3 file + 既存 test で担保 + 挙動変化ゼロ の 4 条件が全部揃うなら黙って潰して結果報告、1 つでも欠けるなら「bug 概要 + 範囲 + 設計判断点」を 3-5 行で操作者に出す
