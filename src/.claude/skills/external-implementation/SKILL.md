# 外部実装を組み込む / 直すとき

**手を動かす前に公式の README と該当コードを読む。**
  - Why: 推測で書いた導入手順は公式と食い違い、直したつもりの箇所が一度も効かないまま積み上がる。落ちた原因が自分の側に見えなくなる

## 読む順

1. **公式の導入手順をそのまま写す** ― 手順の場所と階層をそのまま使う。1 階層違うだけで、存在しない file を探して黙って通るためだ
2. **実行が使う実体はどれかを確かめる** ― clone や checkout が複数あることがある。設定が指す先と、自分が読んでいる先が同じか実物で突き合わせる
3. **import と依存の作りを実物で見る** ― 何を無条件に読むか。拡張は何より先に読む必要があるか
4. **版の固定は公式の指定に従う** ― 外すなら理由を残す。公式が版を書いていないものは、動く組を自分で固定して検査に載せる

## 外の仕組みの file の形は公式の docs で決める

Claude Code の plugin・marketplace・hook・settings のように、file の形を外の仕組みが決めている物は、**形を覚えで書かず、公式の docs を先に開いて写す**。

- 例えば公式の plugin 仕様では、設定は plugin の根の `.claude-plugin/plugin.json`、marketplace は `.claude-plugin/marketplace.json` に置く。skill ・ command ・ hook などの中身は `.claude-plugin/` の中でなく plugin の根に置く。skill は `skills/<名前>/SKILL.md` に置く
- 書いた後は、その仕組み自身の検査まで通して確かめる。plugin では `claude plugin validate <plugin の folder>` を使い、警告を失敗にしたい CI では `--strict` を付ける

## 済んだと言う前に

**入れた / ビルドしたで止めず、使う形で読めることまで確かめる。**
  - Why: install が成功しても、実行時に別の理由で落ちる。「環境は出来た」と報告した後で落ちるのがいちばん高くつく

## 上流を書き換えたら

`third_party` へのパッチは**冪等**にし、台帳へ 1 行残す。当てたあとに構文を機械で確かめる。
  - Why: 当て損なうと上流の file を壊し、次に読む人が公式との差分を追えなくなる
