# ルール台帳と発火記録

ルールの重みを「先に書かれたから残る」ではなく**実測の発火実績**で決めるための機構。 容量上限は残したまま、 枠の中に何が残るかを実績で決める。

## なぜ要るか

- 層の配置が重要度でなく**容量に入るかどうか**で決まっていた (= 大きいものが lazy へ落ち、 毎回効くものが埋もれる)
- 枠が満杯なので、 足すには押し出すしかなく、 押し出す対象を文字数で選んでいた
- どれが効いたかを測っていないので、 退役の判断が感覚だった

## 台帳 (= `rules/registry.jsonl`)

1 行 1 section、 ID は `R-0001` 形式で**一度振ったら不変**。 ID は台帳だけが持ち、 `file` + `heading` で本体と紐付ける (= 本体に書くと常時 load 層の容量を食う)。

- 更新: `python3 .tooling/build-rule-registry.py`
- 検査: 同 `--check` (= 未登録 section / 消滅 section を検出、 docs-check step 11)
- 台帳は**階層ごとに 1 本** (= 1 本にまとめると gitignored な階層の path が tracked file へ漏れる)
- section が消えても行は `retired: true` で残す (= 過去の発火記録が宛先を失わないため)
- `born_date` / `born_subject` = その section が最初に現れた commit (= 出自、 ドリフト確認用)

## 発火記録 (= `journal/<date>/session-NN-rule-hits.jsonl`)

終了時 Step 2 で、 当セッションの実績を触れた階層の journal へ 1 行書く。

```json
{"session":"2026-08-09-02","ts":"2026-08-09T22:10:00+09:00","fired":["R-0012","R-0034"],"violated":[{"id":"R-0056","by":"user"},{"id":"R-0071","by":"self"}]}
```

判定:

- **fired** = そのルールを参照して判断を決めた。 読んだだけ / 該当しなかったものは入れない
- **violated** = 守れなかった。 `by: "self"` = 自分で気づいた、 それ以外 = ユーザに指摘された (= 集計で 3 倍の重み)
- 違反したルールは fired にも入れる (= 発火はしている)
- 迷ったら入れない。 水増しは実績を無意味にする
- **ID は記憶で書かず台帳から引く** (= 思い出した名前で書くと台帳に寄らず、 その記録は集計から落ちる)
- **この形で書く**。 書式が割れると、 集計はその大半を読めない
- 書き漏らした session は `docs-check` step 13 が出す (= その階層が記録を始めた日以降が対象)

## 集計

集計そのものは派生が持つ (= 台帳と記録さえこの書式なら、 出し方は自由)。 集計に要る観点:

- 発火上位 / 違反上位 / 沈黙一覧 (= 押し出しと退役の判断材料)
- 台帳へ寄せられなかった記録の数 (= 書式が割れている分の可視化)
- 記録を書く前に ID を引く手段 (= 語からの検索)

沈黙 = **lazy のルール**が最終発火から **120 日**を超えた状態。 lazy は trigger を踏んだ時だけ読むので「長く読まれない = trigger が一度も来ていない」 が言える。

**常時 load は沈黙判定の対象外**。 毎 session 読まれるが効くかは状況次第で、 発火が無いのは「その状況が来なかった」 だけ (= 破壊操作 / 第三者操作 / メモリ上限)。 そちらの退役は機械で決めず、 読み直して判断する。 記録期間が判定日数に満たないうちは判定を出さない。

## ルールを足す時の判定

1. **破ったら成果かユーザの信頼が壊れるか** → 常時 load 層 (= `rules/always.md` / `profile/profile.md`)
2. **特定の作業中にだけ効くか** → その trigger の lazy
3. **どちらでもない** → **journal に事実として残すだけ**

3 を選べるようにしたのが本機構の要点。 気づいたこと全部をルールにすると枠が飽和し、 押し出しが始まる。

- **機構が守れるものは機構に任せる** (= 本文に書くのは機構が守れない分だけ)
- **保険を書くのは再発を観測してから**。 疑わしい保険は退役 → 再発観測 → 狭い対策
- 真値が 2 箇所以上 → 1 箇所に集約、 残りは参照 1 行

足した後は `build-rule-registry.py` を走らせて ID を採番する。

## 容量超過で押し出す時

静的容量の階層別上限は `rules/always.md § meta` が真値。 ハードなのは階層内の合計だけで、 file ごとの内訳は目安。 動的読込 (= lazy) は上限外。 反応基準は `.tooling/startup-status.sh` の印字が真値で、 容量の緩和は最終手段 (= やるなら単独 commit)。

**押し出す対象は発火実績の下位から選ぶ**。 選ぶ軸は実績だけ (= 文字数で選ぶと、 効いているルールが長いという理由で消える)。

- 実績下位が lazy へ降りる / 沈黙が退役する
- lazy 側で発火が多いものは常時 load へ**昇格**する (= 昇格提案の書式 = `rules/lazy/rule-promotion-format.md`)
- 記録が母数に満たないうちは、 従来どおり判断で削って構わない。 ただし削った ID を journal に残す

## 退役

沈黙が続いたルールは退役候補として起動時に出る。 退役は台帳の `retired: true` と本体からの削除をセットで行い、 ID は一度きりで使い切る。

## どの階層に置くか (= そのルールが偽になる場所で決まる)

偽になる場所が無い (= どのプロジェクトでも真) なら親、 別の repo 群で偽なら `projects/<P>/rules/`、 別のサブプロで偽なら `<S>/rules/`。

- **親の常時 load に固有名詞を書いたら配置違反** (= repo 名 / 製品名 / org 名 / 特定 path / ポート番号)。 その名前を消しても文が成立するまで抽象化するか、 下の階層へ下ろす。 lazy の手順書は対象外 (= 手順は固有名詞で書くもの)
- **その階層固有の対象が 1 つも出てこないルールは上位のもの** (= エージェントの振る舞い / ユーザとの関係は全部親)
- **上位で既に真なことを下位で言い直さない** (= 重複は下位を消す、 参照も置かない)

機械検査 = `docs-check` (= 親の固有名詞 / 参照先の実在)。

## 書くのは時点に依らないものだけ

環境がそうなっている、 を根拠にした記述は環境が変われば黙って嘘になり、 誰も気づかない。

- **書く**: そうすべき理由と、 機械が実在を確かめられる参照先 (= repo 内の path / script 名)
- **外す**: ツールの有無 / ポート番号 / 使用中の path / 台数 / 「現状 N 件」 / その時の担当範囲

## 表現形式

- 基本ペア = 短文 1 行 + `Why: ...` 1 行、 必要時 `How: ...` 1 行。 表は同種要素並列のみ 3 列以内、 散文は file 冒頭 1-2 行のみ
- 除くもの: 過去失敗のラベル化 (= 自己卑下) / 経緯付記 / 強調 3 連語 / 弱表現 (= 「念のため」「一応」)。 履歴の真値は git log / journal / 台帳が持つ

## ルールが増えるのはユーザが言った時だけ

**`rules/` と `CLAUDE.md` はユーザが「追加して」「変えて」 と言った時だけ書く** (= エージェント側の判断では据え置く)。

- 要ると思ったものは journal に候補として残すだけ (= 打診で作業を止めない、 聞かれた時にまとめて出す)
- **違反 2 回観測 → まず detector を書く**。 機械化できないものは文章を足さず journal へ (= 文で書いた保険は守られたか測れないまま枠を食う)
- hit が 1 month 常時 0 の検出 step は廃止 or 基準調整

機構の仕様 = `.tooling/_README.md` + `rules/lazy/automation-machinery.md`。

## rule を改訂した直後にやること

- rule / profile 改訂時は work repo の該当 docs / 設計書 / roadmap を同 session 内 update
- ユーザからのメタ指摘 (= 構造的違反の指摘) はエージェント配下 + work repo docs 両方にそのターン内 commit
- **実測 / 実装で前提を覆したら、 その前提を書いた file を同ターン内で訂正する** (= 自分が反証した記述が残ると、 後から事実としてユーザに渡る)
- エージェント配下の改訂は承認不要、 自発 commit。 work repo docs も自走 update してよい
